# Folki — план нативной реализации

Архитектурное предложение · 17 октября 2026

## Рекомендуемый стек

Swift + SwiftUI для iPhone. Core Data для локального хранения и NSPersistentCloudKitContainer для интеграции с CloudKit. CKShare для приглашения второго пользователя. Системный экран управления доступом — через API, соответствующий выбранной минимальной версии iOS.

Причина выбора: Apple документирует совместное использование объектов Core Data между разными iCloud-пользователями, включая private/shared stores. Для Folki это основной сценарий, поэтому сначала проверяем совместный доступ, затем наращиваем функции. Обычная синхронизация данных одного пользователя между его устройствами не заменяет sharing.

SwiftData можно отдельно оценить на техническом прототипе. Не считать, что включение CloudKit автоматически даёт обмен между двумя Apple ID, и не смешивать прямое управление CKRecord с зеркалированием тех же сущностей Core Data.

## Схема обмена

1. Создатель заводит Household и связанные объекты в private store.
2. Приложение создаёт CKShare для общего набора данных, выдаёт приглашённому право чтения и записи; публичный доступ отключён.
3. Партнёр с собственным Apple ID принимает системное приглашение.
4. Данные владельца остаются в его private CloudKit database; участник обращается к ним через shared database. На устройстве используем два persistent store, а выборку объединяем в репозитории.
5. Изменения сначала сохраняются локально, затем экспортируются и импортируются механизмом CloudKit. UI обновляется из локального хранилища.

Собственный backend для этого сценария не обязателен. Потребуются CloudKit container, настройка capabilities, подпись приложения и аккаунт Apple Developer для конфигурации и распространения. Привязку к команде и контейнеру выполнять с реальными реквизитами владельца проекта.

## Модель данных

| Сущность | Назначение и ключевые поля |
| --- | --- |
| Household | UUID, название, currencyCode, календарь/часовой пояс бюджетных периодов, createdAt |
| Member | UUID, отображаемое имя, связь с идентичностью участника, роль |
| BudgetPeriod | UUID, начало и конец периода, план в минимальных единицах валюты |
| Transaction | UUID, тип expense/income/refund, сумма, currencyCode, categoryID, payerID, authorID, дата операции, название, createdAt, updatedAt, deletedAt |
| Category | UUID, название, SF Symbol, порядок, признак архива |
| Goal | UUID, название, целевая сумма, необязательная дата |
| GoalContribution | UUID, goalID, сумма, участник, дата; допускает обратную операцию изъятия |
| TransactionRevision | UUID, transactionID, автор, время, изменённые поля и предыдущие значения для восстановления |

CloudKit-совместимую схему Core Data проектировать с учётом ограничений зеркалирования: значения по умолчанию/optional, подходящие inverse relationships, отсутствие расчёта на unique constraints. Доменные требования проверять отдельно от требований хранилища.

Суммы — Int64 в минимальных единицах (для RUB — копейки). Форматирование и ввод локализованы. Валюта пространства фиксируется до начала учёта; её смена не должна переименовывать уже введённые суммы без конвертации. Остатки, итоги и процент прогресса вычисляются из операций, а не синхронизируются как изменяемые счётчики.

- Views: Home, Transactions, TransactionEditor, Goals, HouseholdSettings, Invitation, SyncStatus.

Логику расчётов держать независимой от SwiftUI и CloudKit. Модель интерфейса не должна напрямую изменять облачные записи. Не добавлять второй механизм синхронизации поверх NSPersistentCloudKitContainer без отдельной причины.

## Надёжность и доступ

**Асинхронность.** Не обещать мгновенную доставку: задержки зависят от сети и системы. Различать «сохранено на этом iPhone», «ожидает отправки», ошибки доступа и время последнего успешного обмена. Экспорт в CloudKit не равен подтверждению отображения на телефоне партнёра.

**Конфликты.** Для первого прототипа избегать совместно изменяемых итогов; независимые операции имеют UUID. Включить persistent history и обработку remote changes. Merge policy выбрать и проверить на конфликтных изменениях конкретных финансовых полей: автоматическое слияние полей может создать сочетание суммы и категории, которое никто не вводил. История правок и явное разрешение обнаруженного расхождения — часть требований; надёжность этого механизма нужно подтвердить на двух устройствах.

**Повторы.** Один UUID на локальную операцию, защита от двойного нажатия и повторного применения импорта; recurring-платежи позднее потребуют идемпотентного ключа периода. Unique constraints не использовать как облачную гарантию.

**Удаления.** Сначала обратимое soft delete с историей, затем политика очистки. Проверить сценарий, когда второй телефон редактирует уже удалённую запись в офлайне. Обычный выбор merge policy сам по себе не гарантирует корректность этого сценария.

**Личные данные.** Для MVP все операции пространства общие. Если позже появятся личные траты, хранить их в отдельной незашаренной области. Записи владельца в private database, включённые в shared zone, доступны партнёру — название private не означает личный доступ к этим записям.

**Уход из пары.** Владелец может отозвать доступ; у участника он не симметричен владельцу. Перед добровольным выходом предложить экспорт. Уже сохранённые другим человеком копии не отзываются. Перенос владения и продолжение учёта после закрытия пространства требуют отдельного сценария; не обещать автоматическую передачу CKShare.

**Смена Apple ID.** Обработать выход из iCloud, другую учётную запись, потерю доступа, переполненную квоту и недоступный контейнер. Исключить показ данных предыдущего аккаунта новому аккаунту; предложить безопасное восстановление состояния без автоматического удаления ещё не отправленных записей.

## Порядок работ и критерии готовности

### Техническая проверка sharing

Минимальный экран создания пространства и расхода, приглашение, приём и редактирование. Проверить на двух физических iPhone с разными Apple ID в одном CloudKit environment. Подтвердить: запись от каждого участника появляется у другого; офлайн-запись доходит после восстановления сети; повторный запуск не создаёт дубль; отзыв доступа обрабатывается.

### Вертикальная первая версия

Онбординг → приглашение → бюджет → расход → обновлённый остаток → общая цель. Реализовать один выбранный дизайн в SwiftUI, а не переносить все три варианта в продукт. Добавить локальные проверки сумм, возвратов, границ месяцев и отрицательного остатка.

### Подготовка к TestFlight

История правок, конфликты, выход из пространства, ошибки аккаунта, CSV, состояния пустого списка и приглашения. Проверить миграции модели, production schema, общий доступ в TestFlight, Dynamic Type, VoiceOver, тёмную тему и медленную сеть. Debug-сборка с development database и TestFlight с production database не образуют одну тестовую пару.

Сроки оценивать после первого эксперимента с sharing: это наиболее существенная техническая неопределённость проекта.
