# FolkiDuoCore

Чистая финансовая логика: Foundation, без SwiftUI, Core Data и CloudKit. Проверяется через `swift test --package-path Core` на Mac с Swift 6.2+.

## Вход и результат

`HouseholdSnapshot` содержит начальные деньги и резервы на начало периода, свободный месячный план и операции. `DailyBudgetCalculator.calculate(_:asOf:)` получает явное время расчёта; календарь и часовой пояс берутся из `BudgetPeriod`.

Операции до начала периода и позже момента расчёта не входят в результат. Исходные записи не меняются; дубли UUID отклоняются. Для операций с одинаковым временем зачисления в резерв предшествуют списаниям из него; внутри группы порядок стабилизируется UUID. Это устраняет зависимость пополнения/возврата от случайного UUID и порядка импорта. Переводы между резервами должны иметь корректные причинные даты; конфликты совместных записей разрешает будущий слой хранения.

`DailyBudgetSnapshot` — единственный источник дневного остатка, месячного остатка, обеих дуг и прогноза. `PurchaseImpactCalculator` принимает этот снимок и сумму, не создаёт расход и не меняет данные.

## Деньги и округление

Money хранит Int64 минимальных единиц и валюту с явной точностью. Ввод проверяется целиком; `1 234,50` и `1234.50` допустимы, `1.234` для RUB и `123abc` отклоняются. Все сложения и вычитания проверяют переполнение. Double используется только для визуальной доли кольца.

`DailyAllocation` сохраняет каждую минимальную единицу. Первые `extraUnitDays` получают на одну единицу больше `standardAmount`. Поэтому следующий день для 37 550 ₽ / 14 — 2 682,15 ₽, остальные дни могут получить 2 682,14 ₽. Краткое «≈2 682 ₽» в ранних макетах округляло до рублей.

## Резервы и доход

- Покупка из `.flexible` уменьшает свободный остаток и сегодняшний доступный бюджет.
- Оплата `.reserve(id)` уменьшает и деньги, и зарезервированную сумму; свободный остаток второй раз не меняется.
- `reserveAllocation` и `reserveRelease` меняют план, не создавая трат. Остаток резерва не может стать отрицательным.
- Доход по умолчанию `.unallocated`: он не повышает ориентир без явного решения. Для прямого включения дохода в план нужно явно выбрать `.flexible`.
- Возврат учитывается датой операции в заданном периоде. Контроль связи с исходной покупкой и допустимой общей суммы возврата относится к будущему сервису записи; текущий калькулятор работает с уже подтверждённым снимком.
- Отдельный GoalContribution не списывает деньги повторно. Сервис цели создаёт соответствующий перевод резерва атомарно с записью вклада.

Дневной ориентир не сдвигается от сегодняшних покупок. Явные поступления в план и изменения резерва корректируют его базу, потому что меняют сам план. На последнем дне прогноз отсутствует; отрицательный свободный бюджет остаётся дефицитом, а не превращается в разрешённую сумму траты.

## Постоянное хранение: FolkiDuoPersistence

Отдельный target в этом же пакете зависит от FolkiDuoCore и системных CoreData/CloudKit. Само финансовое ядро остаётся независимым от базы.

Текущая версия `FolkiDuoV2.xcdatamodel`, идентификатор `2`; V1 сохранена для миграции: Household, Member, BudgetPeriod, Transaction, Obligation, Reserve, Goal, GoalContribution. Все отношения optional с inverse, без уникальных ограничений и без облачных счётчиков итогов. Обязательные для расчёта значения проверяются при чтении; неполный импорт не подставляет нулевые деньги. Поле мягкого удаления — `tombstone`, чтобы не конфликтовать с `NSManagedObject.isDeleted`.

SQLite private store открывается всегда, shared store — только при явной настройке CloudKit. Включены persistent history, remote-change notifications и автоматическая lightweight migration. Миграция V1→V2 проверяется на настоящем SQLite: прежний бюджет получает scope family, личный не дублируется. Импорт базы исторического Folki-Legacy не заявляется. Для последующих изменений нужно добавить новую версию модели и тест миграции с реальным старым SQLite; не редактировать уже выпущенную V1.

Репозиторий изменяет отдельные операции, а не сохраняет целый JSON-снимок поверх облачной истории. UUID защищает от повторного создания, ревизия — от локального устаревшего редактора. NSError merge policy отклоняет конфликт локальных контекстов. Одновременные офлайн-правки одной записи в CloudKit требуют отдельной проверки и политики в этапе 6: локальная optimistic locking не гарантирует слияние облачных конфликтов.

Статус экспорта учитывает отдельно private/shared stores и изменения, появившиеся во время экспорта. Очередь сохраняется в store metadata. Успех экспорта не означает, что партнёр прочёл запись. Источник финансовых итогов — только исходные операции и начальные деньги/резервы.

`Obligation` подготовлен в схеме. `Goal`/`GoalContribution` используются рабочим сервисом накоплений: создание цели, пополнение и возврат в выбранный бюджет. Возврат сейчас является явной самостоятельной записью; автоматической привязки к исходной покупке и проверки полного лимита возвратов пока нет.


## Два бюджета и накопления

`BudgetScope.personal` и `.family` выбирают независимые корни Household. Личный корень читается только из private store, содержит одного участника и не может стать CKShare. Семейный содержит двух участников и может размещаться в private/shared store. Графы не имеют общих отношений; совпадение UUID автора в двух Member не создаёт связи между ними.

Любое сохранение сверяет scope, Household ID и принадлежность BudgetPeriod. Сервис sharing отдельно проверяет scope корня. Приглашение семейного пространства не требует удаления уже созданного личного бюджета.

Накопления рассчитываются из GoalContribution без изменяемых облачных счётчиков. Пополнение/возврат сохраняют событие и Transaction с тем же UUID в одной транзакции Core Data. Transaction меняет защищённый Reserve, не создавая расход. В новом месяце остаток цели переносится в начальный резерв и вычитается из общей суммы денег один раз.

Перед расчётом проверяется наличие обеих частей перевода с совпадающими суммой, датой, автором и направлением. Неполный импорт не выдаётся за свободные деньги. Такие переводы не редактируются/не удаляются через редактор расходов: обратное действие выполняется возвратом из цели. Обычные расходы и поступления не могут напрямую менять резерв цели.
